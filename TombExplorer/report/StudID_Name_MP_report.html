4. Difficulties and how they were overcome

4.1 A specification with silent spots

Several details that decide the exact output are not in the PDF: how a random number becomes a 40% wall probability, whether prompts end in a newline, what is redisplayed after a rejected command, and what happens when stamina and hearts reach zero in the same move. Because the same seed must give the same dungeon, a wrong guess about the first one changes every map. Approach: each choice was made explicit (decisions D1-D7), isolated in one constant or one function so that it can be changed in one place, and documented.

4.2 The bonus: the number of paths explodes

The automatic mode must collect the maximum value within the remaining stamina. A search over routes has up to 4 choices per step and the stamina allows about 45 steps, i.e. up to 445 ≈ 1.2×1027 walks. That is brute force and is prohibited. Approach: search states instead. A state (Figure 3) is the player's cell, the weapons held, the monsters defeated and the items taken (23 bits). Everything else follows from it: weight and value from the items, steps used from the BFS depth, remaining stamina from the depth. The future of a state does not depend on how it was reached, so each state needs to be expanded only once. With visited flags the search touched a median of about 2×104 states (maximum 3.3×105 in 480 random instances), against 8,388,608 possible states, and takes about 10 ms.

4.3 Guaranteeing "fewest steps, then first found in the order s, w, d, a"

The rule is easy to state but easy to get subtly wrong. Idea: a BFS with "visited on discovery" reaches every state by its alphabetically smallest shortest route. By induction on the depth: entries of one depth are queued in the alphabetical order of their routes; children are generated parent by parent and direction by direction in the order s, w, d, a, so the next depth is queued in the same order, and the first discovery of a state is its smallest route. Moreover, on a shortest optimal route every state lies at its minimum depth (otherwise a shorter prefix would give a shorter route to the same goal state), so remembering one parent per state loses no optimal route. The goal state is therefore chosen by "highest value; then smallest depth; then earliest discovered" (strict comparisons while the BFS runs). This was confirmed against an oracle that finds the alphabetically smallest optimal route with a completely different method.

4.4 No struct or class

A search state naturally wants a record. Approach: pack it into one int (packState()), keep the BFS queue as parallel vectors (state, parent, depth, move, took-item flag), and encode a map cell as row*16+col.

4.5 Verifying without a reference answer

With no sample output to compare to, the risk is bugs that are invisible on a few hand-played games. Approach: differential testing against independent implementations on thousands of random games (Section 2), plus a cross-check that mixes the two programs: the route found by the bonus is replayed by hand in the basic program and must reproduce the predicted value, weight and step count.

Pseudocode of the planner

planRoute():
    start = pack(playerCell, weaponsHeld, monstersDefeated, itemsTaken);  queue = [start];  seen[start] = true
    best = none
    for each entry e of the queue, in order:
        if cell(e) is the exit  or  depth(e) == stamina:  continue
        for dir in (s, w, d, a):
            cell' = neighbour of cell(e) in dir;  skip if outside the map or a wall
            if cell' holds a monster:   skip unless its weapon is held;  mark it defeated;  item = its drop
            if cell' holds a weapon:    mark the weapon as held
            if cell' holds a treasure:  item = that treasure
            options = [ leave ]
            if item exists and is not yet taken and weight(items) + weight(item) <= capacity:
                options = [ take, leave ]                 # "take" is tried first
            for option in options:
                s' = pack(cell', weapons', defeated', items' )
                if not seen[s']:  seen[s'] = true;  enqueue(s', parent = e, move = dir, tookItem = option == take)
                    if cell' is the exit and  (value(items') > bestValue  or  equal value and depth+1 < bestDepth):
                        best = this entry
    if best is none: return "no route"
    follow the parent links from best back to the start  ->  route and take/leave flags

6. Thoughts and suggestions

What the project teaches well

  • Deterministic pseudo-randomness: reproducing a dungeon from a seed forces precise reading of an algorithm, because one different % changes everything.
  • Two classic searches used for what they are good at: BFS for shortest distance and reachability, DFS for exhaustive-but-pruned selection (knapsack).
  • In the bonus, the move from "enumerate paths" to "search states" is a genuine modelling step: choosing what the state must contain, and proving that nothing else is needed.

Suggestions for the specification

  1. State how the random number becomes the 40% wall probability (for example % 100 < 40). This single sentence decides whether every map is right.
  2. Provide one complete worked example: a seed with the resulting map, D, maximum stamina and the first screens, so students can check their generator before building the rest.
  3. Say whether prompts end with a newline or a space, and whether the map and status are redisplayed after an invalid command or a wall bump.
  4. Define the order of the end-of-move checks (item prompt on the last stamina point, stamina and hearts reaching 0 together).
  5. Clarify "brute force": Section 11 asks for a DFS over all 29 combinations, which is itself exhaustive; the wording could say which exhaustive searches are allowed.
  6. Bonus samples contain blank lines between the printed lines; saying whether those are real output (or only the document's spacing) would remove a guess.

Appendix A. Control flow and pseudocode of the basic program

buildDungeon():
    repeat
        for r in 0..15, c in 0..15:  grid[r][c] = (getRandomNum() % 100 < 40) ? '#' : '.'
        grid[0][0] = 'S';  grid[15][15] = 'E'
        D = bfs(0,0)                         # fills reachable[][] ; returns dist to E or -1
    until D >= 0                             # the random stream is NOT reset between attempts
    for symbol in "123456ZVWzvw":
        repeat  row = getRandomNum() % 16;  col = getRandomNum() % 16
        until reachable[row][col] and grid[row][col] == '.'
        grid[row][col] = symbol
    maxStamina = ceil(1.5 * D)

searchBestValue(i, weight, value):           # recursive DFS, items 0..8
    best = max(best, value)
    if i == 9 or value + (sum of positive values of items i..8) <= best:  return
    if weight + w[i] <= capacity:  searchBestValue(i+1, weight + w[i], value + v[i])    # take
    searchBestValue(i+1, weight, value)                                                  # skip

handleMove(cmd):
    (nr,nc) = player + direction(cmd)
    if outside the map: print "You cannot move outside the map." ; return        # free
    if wall:            print "You hit a wall." ; return                          # free
    stamina--;  steps++
    if monster at (nr,nc) and its weapon is missing:
        hearts--;  print "Monster X blocked you." ...;  if hearts == 0 -> lose;  elif stamina == 0 -> lose;  return
    move the player
    if monster: print "You defeated monster X.";  cell becomes its drop
    if weapon:  pick it up;  cell becomes '.'
    if treasure / drop:  offerItem()         # ask y/n until valid; capacity check
    if cell is the exit: win   elif stamina == 0: lose

main():
    read seed, capacity, 9 weight/value pairs;  buildDungeon();  theoreticalMax = DFS
    while game running:  print map + status;  read command;  w/a/s/d -> handleMove ; (r -> auto mode) ; else "Invalid command."
    print map + status + result block
